## 같은 저장소의 기존 비용 산출식에 오류가 있다

`image-text-performance/config/pricing.yaml`의 산출식은 두 곳에서 실제보다 큰 값을 낸다.
두 오차가 같은 방향이라 상쇄되지 않는다.

### 오류 1 — 추론 토큰을 이중으로 계산한다 (출력 비용 최대 2배 과대)

해당 파일의 주석은 다음과 같다.

```yaml
# billable_output = completion_tokens + reasoning_tokens
```

측정으로 확인한 결과는 다르다. GPT-5.6-sol에 `reasoning_effort: "high"`를 지정한
응답의 `usage`는 아래와 같다.

```json
{"prompt_tokens": 24, "completion_tokens": 20, "total_tokens": 44,
 "completion_tokens_details": {"reasoning_tokens": 10}}
```

`total_tokens 44 = prompt_tokens 24 + completion_tokens 20`이다.
추론 토큰이 별도로 계산된다면 총합이 **54**여야 한다.
따라서 **`reasoning_tokens`는 `completion_tokens`에 포함된 내역이며 별도 항목이 아니다.**
Databricks Foundation Model API REST 레퍼런스도 같은 내용을 기술한다.

### 오류 2 — 캐시 토큰을 신규 입력 단가로 계산한다 (입력 비용 최대 10배 과대)

24시간치 실사용 데이터에서 세 모델의 캐시 적중률이 **93~98%**였다.
캐시에서 읽은 토큰은 신규 입력 토큰의 **1/10 단가**다
(Opus 5 기준 7.143 vs 71.429 DBU/1M).

### 이 태스크가 사용하는 산출식

```
USD = usd_per_dbu × ( 신규입력토큰/1e6 × dbu_in
                    + 캐시읽기토큰/1e6 × dbu_cache_read
                    + 캐시쓰기토큰/1e6 × dbu_cache_write
                    + 출력토큰/1e6 × dbu_out )

신규입력토큰 = prompt_tokens − 캐시읽기토큰 − 캐시쓰기토큰
출력토큰     = completion_tokens          ← 추론 토큰이 이미 포함돼 있으므로 더하지 않는다
```

단가는 `image-text-performance/config/pricing.yaml`의 값을 그대로 사용한다
(`usd_per_dbu = 0.07`, Premium Model Serving 표준 단가, 라우팅 global).
구현은 `src/score.py`의 `usd()` 함수다.

## 비용 차이의 상당 부분은 서버가 자동으로 추가하는 프롬프트에서 발생한다

동일한 66개 케이스에 대해 **Opus 5의 프롬프트 토큰 합계는 171,875,
GPT-5.6-sol은 47,760으로 3.6배 차이**다. 케이스와 프롬프트는 같다.
차이는 서버가 도구 정의와 JSON 스키마 전달을 위해 자동으로 덧붙이는 텍스트에서 나온다.
측정값은 [METHODOLOGY §3.5](./METHODOLOGY.md).

**Opus 5와 GPT-5.6-sol의 입력 토큰 단가가 71.429 DBU/1M로 동일하므로
이 토큰 차이가 그대로 입력 비용 차이가 된다.**

도구가 케이스당 5개씩 붙는 FunctionChat-Bench에서 차이가 더 크게 나타난다 —
Opus 5의 프롬프트 토큰이 GPT-5.6-sol의 2.5배다.

> 도구를 많이 쓰는 에이전트에서 Opus 5의 입력 비용은 공시 단가로 계산한 값보다
> 3~4배 높다. 도구 개수에 비례해 증가한다.

## 측정 방법과 신뢰 순위

| 데이터 소스 | 단위 | 이번 실험에서의 사용 |
|---|---|---|
| 응답 본문의 `usage` | **호출 단위** | **주 데이터**. 1,290건 전부 확보 |
| `system.ai_gateway.usage` (요청 태그로 조인) | 호출 단위 | 교차 검증에 사용 |

### 호출 단위 비용 귀속이 가능하다

`mle-benchmark/COST.md`가 기록한 제약은 다음과 같다.

> **태스크 단위 비용을 분리할 수 없음** — 동시 실행 + OpenAI 호환 경로의 토큰 미기록

**API를 직접 호출하므로 이 제약이 발생하지 않는다.** 모든 응답 본문에 `usage`가 있고
그것이 해당 호출의 토큰 수다. 동시 실행 여부나 호출 경로와 무관하다.
따라서 위 표를 실험 조건 × 카테고리 × 반복 어느 축으로도 분해할 수 있다.

### 본 실험 1,290 호출 전수 대조 — 완전 일치

실행 40분 뒤 `src/xcheck.py`로 전수 대조했다.
표기는 `클라이언트 값 / 서버 값`이다.

| 실험 조건 | 호출 수 | 입력 토큰 | 출력 토큰 | 서버 응답시간 중앙값 | 첫 바이트까지 | |
|---|---|---|---|---:|---:|:--:|
| GLM 5.2 | 330 / 330 | 79,590 / **79,590** | 30,710 / **30,710** | 797 | 794 | 일치 |
| Opus 5 (A) | 315 / 315 | 171,875 / **171,875** | 49,388 / **49,388** | 1,800 | 1,798 | 일치 |
| Opus 5 (A′) | 315 / 315 | 171,875 / **171,875** | 56,236 / **56,236** | 1,746 | 1,744 | 일치 |
| GPT-5.6-sol | 330 / 330 | 47,760 / **47,760** | 16,848 / **16,848** | 1,749 | 1,748 | 일치 |

**1,290 호출의 입력·출력 토큰이 전부 일치한다.**
클라이언트 응답의 `usage`를 비용 계산의 주 데이터로 사용할 수 있음이 확인됐다.
`image-text-performance`가 `NotImplementedError`로 남겨둔 `fetch_usage` 자리에
`src/xcheck.py`를 그대로 사용할 수 있다.

#### 대조 과정에서 확인한 사실 — 거부된 요청도 행으로 기록된다

1차 대조에서 Opus 5만 클라이언트 315건 vs 서버 330건으로 수치가 달랐다.
불일치가 아니라 **두 소스가 서로 다른 대상을 집계하고 있었기 때문**이다.

- 서버는 **HTTP 400으로 거부된 요청도 행으로 기록한다**
  (FC-X의 `response_format` + `tools` 조합 15건).
  단 `input_tokens`와 `output_tokens`가 **NULL**이다.
- 클라이언트는 그 요청들을 `gateway_reject`로 분류해 정상 응답 집합에서 제외했다.

→ **토큰·응답시간 통계를 산출할 때 `status_code = 200`으로 필터해야 한다.**
필터하지 않으면 행 수가 어긋나고 NULL 값이 통계에 섞인다.
반대로 이 특성 덕분에 **게이트웨이 거부 건수를 시스템 테이블에서 집계할 수 있다**
(`count_if(status_code <> 200)`). 클라이언트 로그가 없어도 확인 가능하다.

#### 네트워크 왕복 시간

클라이언트 측정 중앙값에서 서버 측정 중앙값을 빼면 네트워크 왕복 시간이 나온다.

| 실험 조건 | 클라이언트 중앙값 | 서버 중앙값 | **왕복** |
|---|---:|---:|---:|
| GLM 5.2 | 949 | 797 | **152 ms** |
| GPT-5.6-sol | 1,944 | 1,749 | **195 ms** |
| Opus 5 (A′) | 1,929 | 1,746 | **183 ms** |

서울에서 이 워크스페이스까지 약 150~200 ms다.
**모델 간 비교에는 서버 측 응답시간이 더 적합하고**(측정 위치의 영향이 제거된다),
**사용자가 실제로 경험하는 것은 클라이언트 측 응답시간**이다.
어느 쪽을 보고하는지 명시해야 한다. [README.md](./README.md)의 응답시간은
클라이언트 기준이다.

> **호출 경로를 잘못 선택하면 교차 검증이 불가능하다.**
> `/serving-endpoints` 경로는 `system.ai_gateway.usage`에 기록되지 않는다
> ([METHODOLOGY §4](./METHODOLOGY.md)). 이 태스크가
> `/ai-gateway/mlflow/v1/chat/completions`를 사용하는 이유다.
>
> 같은 이유로 `image-text-performance/src/cost/usage.py`의 `request_id` 조인 계획은
> 그 벤치마크가 `/serving-endpoints`를 사용하는 한 조인 결과가 비어 있다.

## 이 수치의 한계

- **공시 단가 기반 추정치다.** `system.billing` 조회 권한이 없어 실제 청구액과
  대조하지 못했다. 계약 할인이 있으면 절대값이 달라진다.
  **모델 간 비율은 유효하다**(동일한 단가표를 적용했으므로).
- **`usd_per_dbu = 0.07`은 Premium Model Serving 표준 단가**이며 계약 단가가 아니다.
  이 값만 바꾸면 전체가 재계산된다.
- **라우팅 구분**: Opus 5는 응답의 model 문자열로 Global 라우팅임을 확인했다.
  GPT-5.6-sol은 확인하지 못해 Global로 가정했다(In-geo면 약 10% 높다).
- **캐시 적중이 거의 없었다.** 케이스가 모두 달라 프롬프트 캐시가 적용되지 않았다.
  운영 환경에서 프롬프트가 반복되면 실제 비용은 이보다 낮아진다.
- **원화 환산은 하지 않았다.** 환율을 고정해 기록하지 않으면 여러 날에 걸친 실행에서
  모델과 무관한 변동이 발생한다.
