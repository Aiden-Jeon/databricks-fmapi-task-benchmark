# 데이터셋 출처와 변별력

이 태스크가 사용한 4개 데이터셋의 출처, 각각이 모델을 얼마나 구분하는지,
그리고 **데이터셋에 따라 모델 순위가 뒤바뀌는 현상**을 정리한다.

용어 정의와 재현 절차는 [README.md](./README.md).

---

## 1. 사용한 데이터셋

| 데이터셋 | 출처 | 라이선스 | 건수 | 이 실험의 호출 수 |
|---|---|---|---:|---:|
| 자체 제작 66 | 직접 작성 | — | 66 | 2,310 |
| **FunctionChat-Bench CallDecision** | **카카오** | **Apache-2.0** | **606** | **3,636** |
| **OrchestrationBench** | **카카오** | **Apache-2.0** | 441 | 2,646 |
| 자체 제작 한/영 45쌍 | 직접 작성 | — | 90 | 1,350 |
| **합계** | | | | **9,942** |

외부 데이터셋 두 개가 전체 호출의 **63%**를 차지한다.
두 데이터셋 모두 **데이터를 재배포하지 않고** 변환 스크립트만 이 저장소에 포함한다.

## 2. 자체 제작 케이스는 변별력이 낮았다

각 데이터셋이 세 모델을 얼마나 구분하는지 같은 기준으로 측정했다
(`python3 -m src.discrimination`).

| 데이터셋 | 셀 만점 비율 | 1위–최하위 폭 | 순위 |
|---|---:|---:|---|
| 자체 제작 66 (조건 A) | **92.8%** | 0.045 | sol > opus > glm |
| 자체 제작 한/영 45쌍 | **90.2%** | 0.089 | sol > opus > glm |
| FunctionChat-Bench 전체 606 | 98.0% | 0.015 | **opus > glm > sol** |
| **FunctionChat-Bench CALL 100** | 89.0% | **0.110** | **opus > glm > sol** |
| **OrchestrationBench 한국어 222** | **59.8%** | **0.142** | sol > opus > glm |

*셀 만점 비율 = (케이스 × 실험 조건) 중 반복 전부 정답인 비율. 높을수록 문제가 쉬워
모델이 구분되지 않는다.*

**자체 제작 66개는 셀의 92.8%가 만점이고 1위와 최하위의 차이가 0.045에 불과하다.**
14개 카테고리 중 6개(FC-3, FC-5, FC-6, SO-1, SO-4, SO-5 — 189개 셀)에서
세 모델이 전부 1.000이었다.

OrchestrationBench는 만점 비율이 59.8%로 낮고 차이가 0.142로 세 배 이상 크다.

## 3. 1.000이 전부 케이스 설계 탓은 아니다

자체 제작 케이스에서 FC-5(무관한 요청에 도구를 호출하지 않는가)와
FC-6(정보 부족 시 되묻는가)이 세 모델 모두 1.000이었다.
케이스가 40개뿐이라 표본이 부족했을 가능성을 확인하기 위해,
같은 능력을 측정하는 **외부 데이터 506건**으로 다시 측정했다.

| 카테고리 | 건수 | Opus 5 | GPT-5.6-sol | GLM 5.2 |
|---|---:|---:|---:|---:|
| FCB-REJECT (도구가 부적합 → 호출 안 함) | 100 | 0.990 | **1.000** | 0.995 |
| FCB-SLOT-all (필수 인자 전부 없음 → 되물음) | 100 | 1.000 | 1.000 | 1.000 |
| FCB-SLOT-some (필수 인자 일부 없음 → 되물음) | 306 | 0.997 | **1.000** | 0.998 |

**506건에서도 세 모델이 0.99 이상이다.** 자체 케이스의 1.000은 문제가 쉬워서가 아니라
**세 모델이 이 능력에서 실제로 대등하기 때문**이었다.
외부 데이터가 자체 케이스의 결론을 검증했다.

FCB-SLOT-some 306건 중 207건은 **멀티턴**(최대 3회 사용자 발화)이다.
자체 케이스에 없던 조건인데도 결과가 같았다.

> 채점 범위 주의: 원본 벤치마크는 REJECT / SLOT을 LLM 채점자로 평가해
> "되물음 문장이 올바른 슬롯을 묻는가"까지 본다. 이 저장소는 LLM 채점자를 쓰지 않으므로
> **도구 호출을 억제했는가만** 기계 채점한다. 따라서 위 점수는 원본 리더보드보다 관대하며
> 직접 비교할 수 없다.

## 4. 데이터셋에 따라 순위가 뒤바뀐다

FunctionChat-Bench의 CALL 100건(도구를 호출해야 하는 케이스)에서
**자체 제작 케이스와 순위가 정반대로 나왔다.**

| | 자체 제작 66 | **FunctionChat-Bench CALL 100** |
|---|---|---|
| 1위 | GPT-5.6-sol 0.970 | **Opus 5 0.965** |
| 2위 | Opus 5 0.959 | GLM 5.2 0.935 |
| 3위 | GLM 5.2 0.924 | **GPT-5.6-sol 0.855** |

**GPT-5.6-sol이 1위에서 최하위로 바뀐다.**

### 원인은 능력 차이가 아니라 도구 호출 판단 기준의 차이다

CALL 100건에서 GPT-5.6-sol의 오답 29건 중 **16건이 도구를 호출하지 않고
사용자에게 확인을 요청한 경우**였다.

> 입력: `3월 10일에 제주도로 출장 가는데, 차량 예약이 필요해`
> 정답: `bookBusinessVehicle` 호출
> GPT-5.6-sol: *"차량 예약을 위해 출발 연도를 알려주세요. 현재 날짜가 2026년 8월 7일이라,
> 말씀하신 3월 10일의 연도를 확인해야 합니다."*

> 입력: `2019년 에드 시런 내한공연 인천 콘서트 티켓 두장을 예매할 수 있나요?`
> 정답: `book_concert_tickets` 호출
> GPT-5.6-sol: *"2019년 공연은 이미 종료되어 지금은 예매할 수 없습니다."*

호출해야 하는 100건과 호출하면 안 되는 506건을 함께 집계하면 다음과 같다.

| 모델 | 호출 정밀도 | 호출 재현율 | F1 | 불필요한 호출 | 필요한데 미호출 |
|---|---:|---:|---:|---|---|
| Opus 5 | 0.980 | **1.000** | **0.990** | 4/1,012 | **0/200** |
| GLM 5.2 | 0.990 | 0.990 | **0.990** | 2/1,012 | 2/200 |
| GPT-5.6-sol | **1.000** | 0.920 | 0.958 | **0/1,012** | 16/200 |

*정밀도 = 호출한 것 중 호출해야 했던 비율. 재현율 = 호출해야 할 것 중 실제 호출한 비율.*

**GPT-5.6-sol은 불필요한 호출이 1,012건 중 0건이다.** 도구를 호출하는 기준이
가장 엄격하고, 그래서 REJECT와 SLOT에서 세 모델 중 유일하게 1.000을 기록했다.
같은 성향 때문에 정보가 조금 부족하면 호출 대신 확인을 요청한다.

Opus 5는 반대다. 필요한 호출을 하나도 놓치지 않았지만(재현율 1.000)
불필요한 호출이 4건 있다.

**두 동작은 같은 성향의 양면이며, 어느 쪽이 우수한지는 용도에 따라 다르다.**

- 결제·예약처럼 **잘못된 호출의 비용이 큰 업무** → GPT-5.6-sol
- 조회·검색처럼 **놓친 호출의 비용이 큰 업무** → Opus 5

### 단일 정확도 순위를 신뢰해서는 안 된다

세 데이터셋에서 순위가 두 가지로 갈렸다.

| 순위 | 데이터셋 |
|---|---|
| sol > opus > glm | 자체 제작 66, 자체 제작 한/영 45쌍, OrchestrationBench |
| **opus > glm > sol** | **FunctionChat-Bench** |

갈린 이유는 **데이터셋마다 호출해야 하는 케이스의 비중이 다르기 때문**이다.
자체 제작 66개는 호출 케이스가 대부분이지만 정보가 충분히 주어진 상태였고,
FunctionChat-Bench CALL은 정보가 다소 모호한 상태에서 호출을 요구한다.

## 6. 실행 중 확인한 플랫폼 차이

원본 데이터의 무인자 도구 두 개(`getCurrentKoreaTime`, `getCurrentUTCTime`)는
`parameters`가 빈 객체다. **Opus 5만 HTTP 400으로 거부하고** 나머지 두 모델은 수용한다.
606건 중 73건이 해당하며, 의미가 같은 형태로 정규화해 측정에서 제외했다.
상세는 [METHODOLOGY §3.6](./METHODOLOGY.md).

## 7. 검토했으나 사용하지 않은 벤치마크

사전 조사에서 18개를 검토했고 그중 2개를 실행했다. 나머지를 제외한 이유는 다음과 같다.

| 벤치마크 | 제외 이유 |
|---|---|
| BFCL v4 (Gorilla) | 영어 중심. 한국어 태스크의 목적과 맞지 않는다 |
| τ-bench / τ³-bench | 다중 턴 에이전트 루프가 필요하다. 이 태스크는 단일 호출 측정이 목적이다 |
| JSONSchemaBench | 스키마 준수만 측정하고 도구 호출을 다루지 않는다. SO 트랙 설계에 참고만 했다 |
| Ko-AgentBench | 에이전트 실행 환경이 필요하다 |
| FunctionChat-Bench Dialog 45건 | 채점에 LLM 채점자가 필요해 "LLM 채점자 미사용" 원칙과 충돌한다 |
| FunctionChat-Bench Singlecall 25건 | CallDecision과 측정 대상이 겹치고 건수가 적다 |

## 8. 한계

- **FunctionChat-Bench의 REJECT / SLOT 점수는 원본 리더보드와 비교할 수 없다.**
  LLM 채점자를 쓰지 않아 되물음 내용의 정확성을 확인하지 않았다(§3).
- **반복 횟수가 2회다.** 자체 제작 케이스(5회)보다 적어 `pass^k`를 산출하지 않았다.
- **§4의 확인 요청 16건은 정답 정의의 문제로 볼 여지가 있다.**
  "3월 10일"의 연도를 되묻는 것은 실무에서 적절한 동작일 수 있다.
  원본 벤치마크가 이를 오답으로 정의했고 그 기준을 따랐다.
- **CALL 100건은 표본이 작다.** 1위와 2위의 신뢰구간이 겹쳐
  Opus 5와 GLM 5.2의 차이는 확인되지 않았다.
