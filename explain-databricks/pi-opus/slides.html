The problem

Two stacks, one set of data

Most organizations ended up running a data lake and a data warehouse side by side. Each solves half the problem — and the seam between them is where cost, latency, and trust are lost.

Data lake (object storage)

Cheap, open, scales to petabytes, handles any format — but no transactions, weak schema guarantees, slow BI queries, and easy to turn into a "data swamp".

Data warehouse

Fast SQL, reliable tables, mature governance — but proprietary storage, expensive at scale, and unfriendly to unstructured data, streaming, and machine learning.

The usual workaround is copying data between the two, with separate security models, separate tooling, and separate teams. Every copy is a chance for the numbers to disagree — and for ML models to train on stale data.

The idea

The lakehouse: one copy of the data, both workloads

Databricks' answer is the lakehouse architecture — warehouse-grade reliability, performance, and governance applied directly to open files in your own cloud object storage.

  • Storage stays yours and open. Data lives in S3 / ADLS / GCS as Parquet files with an open table format, not locked inside a vendor engine.
  • Warehouse semantics on the lake. ACID transactions, schema enforcement, and indexing make lake tables trustworthy enough for BI and finance reporting.
  • Every workload, one table. SQL analytics, batch and streaming ETL, and ML/AI training all read the same governed tables — no export, no drift.
  • One governance and security model across data, files, dashboards, and models instead of one per tool.
Short version: data lake economics + data warehouse guarantees, unified.

The building blocks, layer by layer

Databricks is a stack of layers you can adopt incrementally. Each layer depends on the ones below it.

Foundation

Delta Lake: ACID transactions on the lake

Delta Lake is the open table format underneath the lakehouse — Parquet data files plus a transaction log that turns a directory of files into a real table.

  • ACID transactions. Concurrent readers and writers never see partial results; a failed job leaves no half-written table.
  • Time travel & audit. Query or restore any earlier table version (VERSION AS OF) for reproducibility, debugging, and rollback.
  • Schema enforcement and evolution. Bad or changed data is rejected or migrated deliberately, instead of silently corrupting downstream tables.
  • Batch and streaming unified. The same Delta table can be a streaming sink and a BI source — the basis of the bronze → silver → gold "medallion" pattern.
  • Open, not proprietary. Delta Lake is a Linux Foundation project, readable by many engines; UniForm also exposes tables as Apache Iceberg.

Compute & analytics

Apache Spark for scale, Databricks SQL for warehousing

The original Databricks team created Apache Spark. Today the same platform also serves as a serverless data warehouse.

Apache Spark — distributed compute

Parallel processing across a cluster of machines for terabyte-to-petabyte jobs. One engine for batch ETL, Structured Streaming, and SQL, with APIs in Python (PySpark), SQL, Scala, R, and Java. Clusters autoscale and can shut down when idle, so you pay for work rather than idle servers.

Databricks SQL — data warehousing

SQL warehouses give analysts low-latency queries on lakehouse tables via the Photon vectorized engine. Connect Power BI, Tableau, dbt, or JDBC/ODBC tools; build dashboards and alerts in-platform. No data movement — BI reads the same governed Delta tables that engineering writes.

Because storage and compute are decoupled, ETL clusters and BI warehouses scale independently against a single copy of the data.

Governance & automation

Unity Catalog and Workflows

Trust and repeatability: who can see what, and what runs when.

Unity Catalog — governance

One permission model for tables, views, files, dashboards, functions, and ML models, expressed in standard SQL GRANTs over a catalog.schema.table namespace. Adds fine-grained access control (row filters, column masks), automatic column-level lineage, audit logs, data discovery and search, and secure sharing outside the org via Delta Sharing.

Workflows — job orchestration

Native scheduler and orchestrator. Define multi-task jobs as DAGs mixing notebooks, SQL, Python, JARs, and pipelines; set schedules or file-arrival triggers; get retries, conditional branches, alerting, and run history. Declarative pipelines (DLT / Lakeflow) add data-quality expectations and incremental processing — no separate orchestration cluster to run.

Lineage plus job history answers the two questions auditors always ask: where did this number come from, and who could have seen it?

AI on the lakehouse

Machine learning, Mosaic AI, and the Foundation Model API

AI is not a bolt-on product: models are governed assets sitting next to the data they learn from.

  • Classic ML lifecycle. Managed MLflow for experiment tracking, the Unity Catalog model registry, AutoML baselines, and a Feature Store for consistent training/serving features.
  • Mosaic AI is the umbrella for generative AI: Model Serving endpoints, Vector Search for retrieval-augmented generation (RAG), Agent Framework and Evaluation for building and grading agents, and AI Gateway for rate limits, logging, and guardrails.
  • Foundation Model API (FMAPI) gives pay-per-token, OpenAI-compatible access to hosted LLMs and embedding models — plus provisioned throughput for production SLAs — with no GPU cluster to manage.
  • SQL-native AI. Call models straight from queries with ai_query(), ai_classify(), or vector_search() to batch-summarize or classify millions of rows.
  • Governed by the same rules. Prompts, responses, endpoints, and models inherit Unity Catalog permissions, lineage, and audit logging.

Deployment & summary

Multi-cloud by design — and what to remember

Databricks runs as a managed service on AWS, Microsoft Azure (as Azure Databricks), and Google Cloud. Compute runs in your cloud account next to your storage; the control plane (UI, jobs, metadata) is managed by Databricks. Concepts, APIs, and notebooks are portable across all three, which keeps hybrid and multi-cloud estates on one skill set.

One platform

The lakehouse unifies data lake and data warehouse, so engineering, BI, and AI share one copy of the data.

Open foundation

Delta Lake brings ACID transactions to object storage; Apache Spark and Photon provide elastic distributed compute.

Governed by default

Unity Catalog centralizes access control, lineage, and auditing for data, dashboards, and models alike.

Production-ready

Databricks SQL serves BI; Workflows orchestrates jobs and declarative pipelines with retries and alerts.

AI included

Mosaic AI, MLflow, and the Foundation Model API put ML and LLMs where the governed data already lives.

Runs where you are

AWS, Azure, and GCP — the same architecture and APIs, deployed in your own cloud accounts.

A good first step: land raw data as Delta tables, register them in Unity Catalog, schedule the pipeline with Workflows, then point Databricks SQL and Mosaic AI at the same tables.
