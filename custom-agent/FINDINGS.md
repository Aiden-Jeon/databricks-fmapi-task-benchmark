# FINDINGS — Custom Agent 성능

## 1. 정확도로는 세 모델이 구분되지 않는다

12 케이스 × 5 회를 opus / sol / glm 이 전부 통과했다. pass^5 = 1.00 (모든 arm × 시나리오).
초기 채점에서 보인 차이는 실제 응답 대조 결과 전부 scorer 아티팩트였다(METHODOLOGY §4.4).

난이도를 의도적으로 높인 케이스도 셋 다 맞혔다:
- **최신 자료 필요** — A-5(DBFS init script 지원 종료, 2023-12-01 EoL), A-6(DBFS 루트/마운트 비활성화).
  학습 시점 이후 바뀐 플랫폼 규칙이라 기억에 의존하면 "DBFS 권한/경로를 고치라"는 옛 답을 낸다.
  세 모델 모두 `get_doc` 를 조회해 현재 상태(폐지 → Volumes/Workspace files 로 이관)를 정확히 답했다.
- **강한 도메인 함정** — B-5(갑상선암). "암이니 진단금 전액"이라는 강한 사전지식과 반대로,
  이 상품에서 갑상선암은 통합소액암(200만)이고 통합암진단특약에서 제외된다. 세 모델 모두
  `lookup_disease_code` 와 조항을 읽고 200만으로 답했다. 아무도 1,000만 함정에 빠지지 않았다.
- **구간 판별** — B-3(다빈치 180일 이내 25%)과 B-6(180일 초과~1년 50%)은 날짜만 다르다.
  세 모델 모두 각 사건의 경과일을 세어 올바른 구간을 골랐다.

**해석**: 이 모델들은 사전지식을 답으로 흘리지 않고 도구·문서가 준 사실에 근거해 판단한다.
그래서 함정과 최신 정보 케이스가 변별에 실패했다. 이는 프론티어 모델의 도구 기반 추론이
이 난이도에서 이미 충분히 견고하다는 뜻이다.

## 2. 변별은 비용과 지연에서 극명하다

| 모델 | 세션당 비용 | 중앙 지연 | p90 지연 | 평균 스텝 |
| --- | --- | --- | --- | --- |
| opus | $0.1157 | 31.5s | 39.5s | 4.3 |
| sol | $0.0354 | 12.3s | 14.6s | 3.8 |
| glm | $0.0077 | 15.8s | 22.2s | 4.2 |

- **비용**: opus 가 glm 의 **14.9배**, sol 의 3.3배. glm 은 정확도 손해 없이 압도적으로 싸다.
- **지연**: sol 이 가장 빠르다(중앙 12.3초). opus 는 adaptive reasoning 때문에 2.5배 이상 느리다.
- **스텝**: 셋이 비슷하다(3.8~4.3). 도구 선택 효율은 대동소이.

## 3. 스텝·도구 사용 관찰

- 세 모델 모두 필수 도구를 빠짐없이 호출했다(tool coverage 1.0). distractor 도구(예: Azure 10개 중
  케이스와 무관한 것)를 일부 조회하기도 했으나 최종 판정에는 영향이 없었다.
- A-2(DNS)에서 jumpbox·cluster nslookup 결과의 **차이를 비교**하는 핵심 추론을 셋 다 수행했다.
- A-4 fault(첫 `get_job_run` 503)에서 셋 다 재시도로 복구해 원인에 도달했다.

## 4. 결론

이 벤치마크의 실무 함의는 명확하다. **중상도 업무형 에이전트 태스크에서 세 모델의 정확도가 같다면,
모델 선택은 비용·지연 문제로 귀결된다.** glm 은 정확도를 지키면서 opus 대비 15배 저렴하고, sol 은
가장 빠르다. opus 의 추가 비용·지연을 정당화하려면 이보다 어려운 — 정확도가 실제로 갈리는 —
태스크가 필요하다. 이 케이스 셋에서는 그 지점을 찾지 못했다.

## 5. 한계

- 케이스 12개로 정확도 CI 하한이 0.88~0.89 수준이다. 표본이 작아 미세한 정확도 차이는 못 잡는다.
- 정답성 채점이 정규식 기반이라 표현이 다른 정답을 놓칠 위험이 있다. 실제로 두 건을 재교정했다(§4.4).
  경계 사례는 사람이 응답을 직접 확인하는 것이 안전하다.
- 도구가 전부 Mock 이라 실제 API 지연·오류·부분 실패의 다양성은 재현하지 못한다.
